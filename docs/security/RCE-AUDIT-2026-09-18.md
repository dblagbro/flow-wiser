# RCE audit — 2026-09-18

Point-in-time record. Focused remote-code-execution review of `apache2-only` @ `a28bc9ea`,
plus the production posture of `dblagbro/flow-wiser:3.1.4-fw10-askdevin3`.

## Verdict

**Code-level RCE defenses are strong and actively maintained.** One material finding, and it is
**operational, not code**: production runs the vm2 code-execution engine (the default), which is
deprecated and unpatchable. Verified that **0 of 25 production flows use any code-execution node**
and **0 flows are public**, so `CODE_EXECUTION_MODE=disabled` removes the entire risk class **at no
functional cost**. Recommended.

## The finding — production runs vm2 (operational)

-   No `CODE_EXECUTION_MODE` set and no `E2B_APIKEY` in the production container → mode resolves to
    `vm2`. `TOOL_FUNCTION_BUILTIN_DEP`/`_EXTERNAL_DEP` are set.
-   vm2 is deprecated and unpatchable. The in-process mitigations block _published_ escapes but cannot
    guarantee safety against a novel one. Anyone who can author or influence a code-execution node is,
    in principle, one vm2 escape from host RCE.
-   **Practical exposure is currently low but not zero:** verified 0/25 flows use a code node
    (`customFunction`, `customTool`, `ifElseFunction`, sequential-agent code nodes, `codeInterpreterE2B`,
    `chatflowTool` — all zero), 0 flows contain inline `javascriptFunction`, and 0 flows are public.
    The engine is nonetheless live and would execute code the moment a code node is added or the admin
    account is compromised.

**Recommendation:** set `CODE_EXECUTION_MODE=disabled` on production (in the `.env`, then
`docker compose up -d --force-recreate --no-deps flowise`). It breaks nothing here and removes the
risk class. If code execution is wanted later, `CODE_EXECUTION_MODE=e2b` + an E2B key runs it
off-host. Tracked as **I-29** (register) and **SEC-B-11** (bug-log).

## Coverage / not covered

Covered: code execution + require allowlist, vm2 escape primitives, command-exec sinks, SSRF
redirect/rebind, SSTI, prototype pollution, deserialization, and a production flow-usage check.
**Not exhaustively traced:** file-upload → local path-traversal → write (the upload path validates
mime/extension and targets the OpenAI API, but the full write path was not walked end to end);
a live re-test of every outbound fetch call site against `httpSecurity`; and a public-PoC check for a
vm2 3.11.6-specific escape (none needed for the recommendation, since the fix is to disable).
